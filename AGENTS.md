# AGENTS.md

**This file is the source of truth for agent instructions.** Claude Code (2.1.277 and later), Cursor, Codex and other tools that follow the AGENTS.md convention read it directly. Add agent guidance here and nowhere else, and do not add a `CLAUDE.md`: Claude Code reads `AGENTS.md` only when no `CLAUDE.md` exists.

## What this is

A NixOS flake meant to be forked (the kickstart.nvim model): a readable starting point, not a framework. Forks rename the example user and host, then grow their own system. Desktops and Raspberry Pi hosts are both in scope. User-facing behavior is documented in `README.md` and `docs/`; this file covers what an agent needs to change the code safely.

## Commands

| Goal | Command |
|---|---|
| Make a fresh fork yours: write its host, remove the examples (`--help` for the flags) | `nix run .#init` |
| Install the pre-push hook (once per clone), get `sops` and `age` | `nix develop` |
| Run the pre-push hook by hand | `nix develop -c pre-commit run --hook-stage pre-push --all-files` |
| Format and lint (nixfmt, statix, deadnix) | `nix fmt` |
| All checks: lint, host builds, boot tests | `nix flake check -L` |
| One check | `nix build -L .#checks.x86_64-linux.<name>` |
| Checks the CI matrix runs, with system and runner | `nix eval --json .#ci.matrix` |
| Build the VM | `nix build .#nixosConfigurations.<host>.config.system.build.vm` |
| Boot the VM headless (blocks until killed) | `QEMU_KERNEL_PARAMS=console=ttyS0 ./result/bin/run-<host>-vm -nographic` |
| Build the installer ISO of a host with `disk` | `nix build .#installer-<host>` |
| Regenerate `docs/options.md` after changing the registry options | `nix run .#options-doc` |
| Package diff against a revision | `nix run .#closure-diff -- <rev>` |
| Evaluate an `aarch64-linux` check (`nix flake check` skips other systems) | `nix eval --raw .#checks.aarch64-linux.<name>.drvPath` |
| Lint workflows | `nix run nixpkgs#actionlint` |

A flake only sees files tracked by git: `git add` new files (staging is enough) before any `nix` command, or they are silently missing.

## Architecture: the dendritic pattern

The flake is built with flake-parts, and `flake.nix` hands the whole `modules/` tree to `import-tree`.

- **Every `.nix` file under `modules/` is a flake-parts module**, imported automatically. Adding a file adds the feature, deleting it removes it. A path segment starting with `_` is ignored.
- **NixOS and home-manager config is published, not imported.** A file contributes to `flake.modules.nixos.<name>` or `flake.modules.homeManager.<name>`; several files may write to the same name (`base` is assembled by `system/nix` and `system/home-manager`) and the module system merges them.
- **A host is a registry entry in plain values.** `modules/flake/hosts/options.nix` defines `configurations.nixos.<name>`; every field is in `docs/options.md`, generated by `nix run .#options-doc` (the `options-doc` check fails when it is stale). Names (`profile`, `features`, `apps`, `hardware`, `home`) are lists, never `enable` booleans, and become imports at the flake-parts level, in the registry's `config.module`: never translate them from inside a NixOS module. An unknown name throws with the known ones. `apps` resolves to `apps.<name>` (`modules/flake/hosts/apps.nix`, a `nixos` and a `homeManager` part imported with a `key`), else to `pkgs.<name>` with its unfree name allowed; `hardware` resolves to `flake.modules.nixos.<name>`, else to a nixos-hardware profile. The registry sets `nixpkgs.hostPlatform` itself: never set it in a module. A host name has 1 to 63 letters, digits, `-` and `_`, starting and ending with a letter or digit.
- **No registry field names a device.** The disk is the `disk` feature; it is chosen at install (installer ISO, `disko-install --disk main`, or `module.disk.device` for nixos-anywhere), `disk.device` defaults to `/dev/null/no-disk-chosen`, and the installed system mounts by partlabel.
- **A user is a registry entry.** `users.<user>` creates the account (`wheel` when `admin`, password from `/persist/passwords/<user>` with persistence, `test` in the VM) and its home-manager config. A fork's own home config is a `flake.modules.homeManager.<user>` the user lists in `home`; nothing is imported by matching a user name.
- **Checks are generated, not listed.** Every host gets `<name>-toplevel` and `<name>-boots` (a NixOS test waiting for `multi-user.target` and every `home-manager-<user>.service`), or `<name>-sd-image` for a host with an SD image. A host with `disk` gets `<name>-disk` (disko's install test: format, install, reboot, then `modules/system/disk/wipe-test.py`, `modules/system/snapshots/snapshot-test.py` and `modules/system/doctor/disk-test.py`; Secure Boot and TPM2 under OVMF when it also imports `secure-boot`), and `<name>-wipe-home` when it lacks `wipe-home`. A host importing `hibernate` runs `<name>-disk` with a 1G swap file, since the test disk has 4 GiB; `system-hibernate` installs a minimal `disk` and `hibernate` machine, copies its store onto the disk (like nixpkgs' own hibernate test, it does not resume on a store shared with the host), hibernates, resumes and reboots it. Hosts in `installer.testedHosts` get `<name>-installer`. Module tests go through `helpers.profileCheck`, `helpers.baseCheck`, `helpers.appCheck` or `helpers.vmCheck` (`x86_64-linux` only). `flake.ci.matrix` lists every check with its runner, and `ci-plan` (`modules/flake/ci/ci-plan.sh`) drops what the binary cache holds and, in a PR, any check that builds a host kernel.
- **Helpers** live in `config.helpers` (`modules/helpers/`, one file per topic); read them with `inherit (config.helpers) <name>;`. Home and desktop values go through `helpers.mkDefaults` so a user overrides them without `mkForce`; lists meant to be extended stay plain.

Layers under `modules/`, one folder per tool, never a loose `.nix` file at layer level (`helpers/` excepted): `flake/` (wiring, registry, checks, installer, `init`, dev shell, CI scripts), `helpers/`, `system/` (base with `update` and `doctor`, and opt-in `disk`, `impermanence`, `wipe-home`, `hibernate`, `snapshots`, `secure-boot`, `ssh`, `secrets`, `auto-upgrade`), `hardware/`, `profiles/` (`desktop`, `laptop`, `server`, `pi`), `dev/`, `home/`, `apps/`, `desktop/`, `users/` and `hosts/`. `users/` and `hosts/` belong to the fork: upstream keeps them minimal (`example`, `example-server`, `example-pi`) so forks merge upstream without conflicts. `nix run .#init` (`modules/flake/init/init.sh`) writes a fork's first host from `modules/hosts/example/default.nix` and removes the examples; it toggles the `"name" # description` lines of the `features`, `hardware` and `apps` lists and rewrites the plain fields by their line, so keep that layout; the `init` check runs it on a copy of the flake.

Starter-owned modules stay generic: no user name, host name, path or personal value in them. Personal values belong in `hosts/` and `users/`, or behind an option with a neutral default.

## Pitfalls already hit

- **`let` shadows `with`.** In `with config.flake.modules.nixos; [ desktop ]`, a `let desktop = ...` in scope silently wins. Never bind a name that matches a module name.
- **`nix flake check` builds the boot test**; a passing `nix eval` does not mean the system boots.
- **`/` is wiped at every boot.** State written outside `/nix`, `/home`, `/persist` and `/.snapshots` disappears unless added to `environment.persistence."/persist"`, declared in the module that owns the state, never in a central list. State meant to vanish goes in `doctor.ephemeralPaths` from the same module, so `doctor` does not report it as lost. State in a home goes through `home.persistence."/persist".directories` (relative to the home, `helpers.relativeToHome`), or `helpers.persistInEveryHome` from a NixOS module; it only applies on hosts with `wipe-home`.
- **State read during activation lives under `config.impermanence.persistPrefix`.** Activation scripts (sops-nix) run before the impermanence bind mounts exist: point such paths at `/persist` through the prefix, as `ssh` and `secrets` do.
- **`home-manager-<user>` fails inside `<name>-disk`.** disko's harness mounts the host store over 9p and `nix-daemon` cannot chown it; the wipe test does not wait for it, `<name>-boots` covers home-manager.
- **No key file next to `tpm2-device`.** systemd-cryptsetup then reads the key file as a TPM token and never tries the TPM. Tests unlock LUKS by typing the passphrase on the console (`modules/system/disk/unlock-disk.py`).
- **The volume key of an open LUKS2 device is not readable** through dm-crypt. `tpm2-enroll` uses the `user` copy the initrd links with `link-volume-key=`, passed as `%user:<name>`; the initrd drops it once a token exists, else after 300 s.
- **Wait for the password agent, not for its unit.** Wait for `password query on /dev/tty1`, or with Plymouth for `Please enter passphrase for disk`; keys sent earlier are lost.
- **Hyprland needs a DRM device in the VM**: `-vga none -device virtio-gpu-pci`.
- **nixos-raspberrypi's prebuilt kernels come from its own nixpkgs pin**: `hardware/raspberry-pi` builds the kernel and firmware from our `pkgs` (`mkOverride 900`), so its binary cache has no hit for them.
- **`nix flake check` only evaluates the current system.** Evaluate `aarch64-linux` checks with `nix eval` and let CI build them.
- **Unfree packages go through `nixpkgs.config.allowUnfreePackages`** : a module adds its `lib.getName` to the list; `allowUnfree = true` would make every list moot. The boot test runs with `node.pkgsReadOnly = false` so host `nixpkgs.*` settings apply.
- `warning: unknown flake output 'modules'` is expected and harmless.

## CI

Workflows in `.github/workflows/` only chain one-line calls. Any logic goes into Nix (`flake.ci.*`) or into a shell script under `modules/flake/ci/`, packaged with `writeShellApplication` and called with `nix run .#<name>`. Never write a multi-line script inside a workflow. The `ci-ok` job is the single required status check on `main`. `release` runs in the starter only and `sync-upstream` in forks only, both keyed on `github.repository`. Details: `docs/ci.md`.

## Conventions

- **No comments** in `.nix` and `.sh` files: names carry the intent. Tool directives stay. One exception: `modules/hosts/example/default.nix` is commented, read top to bottom by a forker. Every registry field has one or two lines, and every profile, feature, hardware module and app the starter ships has one line, enabled or commented out; a new one is added there too.
- Code, docs, commits and README in English. No em dash or en dash anywhere.
- Conventional Commits (`feat`, `fix`, `refactor`, `docs`, `chore`, `ci`), subject describing the observable effect, lowercase, no trailing period, at most 72 characters; prose body explaining why when not trivial. release-please opens the release PR on `main`: never set a version, edit `.release-please-manifest.json`, `version.txt` or `CHANGELOG.md`, or create a tag by hand. The project stays in `0.x` with every release marked as a pre-release until the maintainer decides on `1.0.0`.
- Branches `feat/`, `fix/`, `refactor/`, `chore/`, `docs/` from `develop`; PR into `develop`, then `develop` into `main` with a merge commit, never squashed. `main` only moves through PRs.
- `ROADMAP.md` lists shipped lots and their guardrail checks; update it in the commit that ships a lot.
- The pre-push hook runs treefmt, `nix flake check --no-build` and actionlint in seconds; builds and boot tests are left to CI. Never bypass it with `--no-verify`.
- Stage files one by one. Never commit or push without the maintainer's explicit go: show the staged diff and wait.

## Safety

Everything is developed and tested in VMs. Never run disko, `nixos-install`, `nixos-rebuild switch`, `bootctl`, `sbctl` or any partitioning command against a physical disk or the host machine without an explicit request naming the target.

## Done means

1. `nix fmt` leaves nothing to change and `nix flake check -L` ends with `all checks passed!`
2. `nix run nixpkgs#actionlint` is clean when workflows changed
3. A change with an observable effect is shown running: VM boot, `closure-diff`, command output
4. README and `docs/` still match the code
