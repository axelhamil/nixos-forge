# AGENTS.md

**This file is the source of truth for agent instructions.** Claude Code (2.1.277 and later), Cursor, Codex and other tools that follow the AGENTS.md convention read it directly. Add agent guidance here and nowhere else, and do not add a `CLAUDE.md`: Claude Code reads `AGENTS.md` only when no `CLAUDE.md` exists.

## What this is

A NixOS flake meant to be forked (the kickstart.nvim model): a readable starting point, not a framework. Forks rename the example user and host, then grow their own system. Desktops and Raspberry Pi hosts are both in scope. User-facing behavior is documented in `README.md` and `docs/`; this file covers what an agent needs to change the code safely.

## Commands

| Goal | Command |
|---|---|
| Make a fresh fork yours: write its host and person, remove the examples (`--help` for the flags) | `nix run .#init` |
| Install the pre-push hook (once per clone), get `sops` and `age` | `nix develop` |
| Run the pre-push hook by hand | `nix develop -c pre-commit run --hook-stage pre-push --all-files` |
| Format and lint (nixfmt, statix, deadnix) | `nix fmt` |
| All checks: lint, host builds, boot tests | `nix flake check -L` |
| One check | `nix build -L .#checks.x86_64-linux.<name>` |
| Checks the CI matrix runs, with system and runner | `nix eval --json .#ci.matrix` |
| Build the VM | `nix build .#nixosConfigurations.<host>.config.system.build.vm` |
| Boot the VM headless (blocks until killed) | `QEMU_KERNEL_PARAMS=console=ttyS0 ./result/bin/run-<host>-vm -nographic` |
| Build the installer ISO of a host with `disk` | `nix build .#installer-<host>` |
| Regenerate `docs/options.md` after changing the registry options | `nix run .#options-doc` |
| Package diff against a revision | `nix run .#closure-diff -- <rev>` |
| Show what the starter changed and prepare its merge in a fork | `nix run .#upstream` |
| Evaluate an `aarch64-linux` check (`nix flake check` skips other systems) | `nix eval --raw .#checks.aarch64-linux.<name>.drvPath` |
| Lint workflows | `nix run nixpkgs#actionlint` |

A flake only sees files tracked by git: `git add` new files (staging is enough) before any `nix` command, or they are silently missing.

## Architecture: the dendritic pattern

The flake is built with flake-parts, and `flake.nix` hands the whole `modules/` tree to `import-tree`.

- **Every `.nix` file under `modules/` is a flake-parts module**, imported automatically. Adding a file adds the feature, deleting it removes it. A path segment starting with `_` is ignored.
- **NixOS config is published, not imported, in the namespace of the registry field that names it.** `modules/flake/hosts/namespaces.nix` declares one flake-level option per field: `base` (one module, always on), `profiles.<name>`, `features.<name>` and `hardware.<name>` (NixOS modules, each wrapped with the `key` `nixos-starter/<field>/<name>` so it is imported once), and `apps.<name>` (a `nixos` and a `homeManager` part each, imported with `_class` set to the part, so a home-manager module in a `nixos` part throws). People are the flake-level `users.<name>` of `modules/flake/hosts/users.nix`. A folder publishes into the namespace of its place: `modules/features/<name>` into `features.<name>`, `modules/features/profiles/<name>` into `profiles.<name>`, `modules/features/hardware/<name>` into `hardware.<name>`, `modules/features/base/<tool>` into `base`, `modules/apps/<name>` into `apps.<name>`. Several files may write to the same name (`base` is assembled by every `features/base/<tool>`; `disk` also by `features/disk/snapshots`, a sub-folder of the feature it extends) and the module system merges them (`hyprland` from `default.nix` and `home.nix`). `flake.modules.nixos.<name>` and `flake.modules.homeManager.<name>` are outputs only, mapped by `modules/flake/flake-parts/modules.nix` from `base`, the three namespaces and the apps' parts some file defines (an app with no `nixos` part is not in `flake.modules.nixos`) for other dendritic flakes to import; nothing in the flake reads them or writes them otherwise. A name published by two namespaces throws, and the `flake-modules` check forces that guard.
- **A host is a registry entry in plain values.** `modules/flake/hosts/options.nix` defines `configurations.nixos.<name>`; every field is in `docs/options.md`, generated by `nix run .#options-doc` (the `options-doc` check fails when it is stale). Names (`profile`, `features`, `apps`, `hardware`) are lists, never `enable` booleans, and become imports at the flake-parts level, in the registry's `config.module`: never translate them from inside a NixOS module. Each field resolves in its own namespace only: `profile` resolves to `profiles.<name>`, `features` to `features.<name>`, `hardware` to `hardware.<name>`, else to a nixos-hardware profile, and `apps` to `apps.<name>` (its `nixos` part on the host, its `homeManager` part for every user, or for one user from the person's or the host user's `apps`, both imported through `helpers.appPart` with the `key` `nixos-starter/apps/<name>/<part>`, so an app reached twice is imported once, which the `apps-once` check proves), else to the nixpkgs attribute path `pkgs.<name>` with its unfree name allowed. An unknown name throws naming the field: for `profile`, `features` and `hardware` it lists that namespace alone; for `apps` it lists the configured apps and says any nixpkgs attribute path also works, so `apps = [ "docker" ]` installs `pkgs.docker`; for `users` it lists the people of `modules/users`. The `wrong-namespace` check proves the five messages. An app that brings others (`shell`: `zsh`, `starship`, `git`, `neovim`, `cli`; `hyprland`: the `greetd` feature, `lock`, `waybar`, `kitty`, `mako`, `fuzzel`) imports them with `helpers.appPart`, never through `flake.modules`. The registry sets `nixpkgs.hostPlatform` itself: never set it in a module. A host name has 1 to 63 letters, digits, `-` and `_`, starting and ending with a letter or digit.
- **No registry field names a device.** The disk is the `disk` feature; it is chosen at install (installer ISO, `disko-install --disk main`, or `module.disk.device` for nixos-anywhere), `disk.device` defaults to `/dev/null/no-disk-chosen`, and the installed system mounts by partlabel.
- **A person is defined once, an account per host.** `modules/users/<user>/default.nix` sets the flake-level `users.<user>`: `fullName`, `email`, `sshKeys`, `apps` (`[ "shell" ]` by default, on every host) and `module`, the person's own home-manager config (wrapped with the `key` `nixos-starter/users/<user>` and `_class = "homeManager"`; several files of the folder may each set part of it). A host's `users.<user>` holds per-machine fields only (`admin`, `groups`, `apps` added to the person's) and creates the account (`wheel` when `admin`, password from `/persist/passwords/<user>` with persistence, `test` in the VM) with its home-manager config: the host's `apps`, the person's and the host user's, then the person's `module`. zsh is the login shell when one of those lists names `shell` or `zsh`. A host naming a person with no `modules/users/<user>` throws with the known people.
- **Checks are generated, not listed.** Every host gets `<name>-toplevel`, the real system with its real `configurationRevision`, which CI caches for `auto-upgrade`, and `<name>-boots` (a NixOS test waiting for `multi-user.target` and every `home-manager-<user>.service`), or `<name>-sd-image` for a host with an SD image. Every test machine pins `configurationRevision` to `"test"` through `helpers.testRevision`, so test derivations stay cached from one commit to the next. A host with `disk` gets `<name>-disk` (disko's install test: format, install, reboot, then `modules/features/disk/wipe-test.py`, `modules/features/disk/snapshots/snapshot-test.py` and `modules/features/base/doctor/disk-test.py`; Secure Boot and TPM2 under OVMF when it also imports `secure-boot`), and `<name>-wipe-home` when it lacks `wipe-home`. A host importing `hibernate` runs `<name>-disk` with a 1G swap file, since the test disk has 4 GiB; `feature-hibernate` installs a minimal `disk` and `hibernate` machine, copies its store onto the disk with `helpers.storeOnDiskTest` (like nixpkgs' own hibernate test, it does not resume on a store shared with the host), hibernates, resumes and reboots it. `feature-rollback` (`modules/features/auto-upgrade/rollback-check.nix`) installs a minimal `disk` and `auto-upgrade` machine, and `feature-rollback-secure-boot` the same with `secure-boot` under OVMF after the TPM2 enrollment; both copy the store onto the disk (nix cannot open the store shared over 9p), install a second generation whose failing service keeps `systemd-boot-check-no-failures` from blessing it, boot it 3 times (`+2-1`, `+1-2`, `+0-3`) and check the next boot starts generation 1 again. Hosts in `installer.testedHosts` get `<name>-installer`. Module tests are named after their namespace and go through `helpers.baseCheck` (`base-<tool>`), `helpers.featureCheck` (`feature-<name>`), `helpers.profileCheck` (`profile-<name>`), `helpers.appCheck` (`app-<name>`, with the app's two parts for a `tester` user) or `helpers.vmCheck` (`x86_64-linux` only). `flake.ci.matrix` lists every check with its runner, and `ci-plan` (`modules/flake/ci/ci-plan.sh`) drops what the binary cache holds and, in a PR, any check that builds a host kernel.
- **Helpers** live in `config.helpers` (`modules/flake/helpers/`, one file per topic); read them with `inherit (config.helpers) <name>;`. App values go through `helpers.mkDefaults` so a user overrides them without `mkForce`; lists meant to be extended stay plain.

Layers under `modules/`, one folder per tool, never a loose `.nix` file at layer level (`flake/helpers/` excepted): `flake/` (wiring, registry, checks, installer, `init`, `upstream`, dev shell, CI scripts, `helpers/`), `features/` (`base/` with `nix`, `home-manager`, `impermanence`, `memory`, `resolved`, `nix-index`, `doctor` and `update`; `profiles/` with `desktop`, `laptop`, `server`, `pi`; `hardware/`; and one folder per feature: `disk` (with `snapshots/`), `wipe-home`, `hibernate`, `secure-boot`, `ssh`, `secrets`, `auto-upgrade`, `docker`, `libvirt`, `nix-ld`, `greetd`, `plymouth`), `apps/` (everything a user runs, with its config: `hyprland`, `waybar`, `kitty`, `mako`, `fuzzel`, `lock`, `zsh`, `starship`, `git`, `neovim`, `cli`, `shell`, `direnv`, `stow`, `firefox`), `users/` (one folder per person) and `hosts/`. `users/` and `hosts/` belong to the fork: upstream keeps them minimal (the person `alice`, the hosts `example`, `example-server`, `example-pi`) so forks merge upstream without conflicts. `nix run .#init` (`modules/flake/init/init.sh`) writes a fork's first host from `modules/hosts/example/default.nix` and its person from `modules/users/alice/default.nix`, renames `users.alice = {` in the example hosts it keeps and points their `flake = "github:` line at the fork read from the `origin` remote, or comments it out with their `"auto-upgrade"` line when there is none or it is the starter, and removes the examples; it toggles the `"name" # description` lines of the `features`, `hardware` and `apps` lists, rewrites the plain host fields (`system`, `profile`, `flake`, `timeZone`, `locale`, `keyboard`, the `users.alice = {` line) and person fields (`users.alice = {`, `fullName`, `email`) by their line, and replaces `alice` in the person's comments, so keep that layout; the `init` check runs it on copies of the flake and evaluates the `toplevel.drvPath` of every host left, with this flake's locked inputs (`modules/flake/init/_call-fork.nix`, no fetch, no import from derivation).

Starter-owned modules stay generic: no user name, host name, path or personal value in them. Personal values belong in `hosts/` and `users/`, or behind an option with a neutral default.

## Pitfalls already hit

- **`let` shadows `with`.** In `with config.profiles; [ desktop ]`, a `let desktop = ...` in scope silently wins. Never bind a name that matches a module name.
- **`nix flake check` builds the boot test**; a passing `nix eval` does not mean the system boots.
- **`/` is wiped at every boot.** State written outside `/nix`, `/home`, `/persist` and `/.snapshots` disappears unless added to `environment.persistence."/persist"`, declared in the module that owns the state, never in a central list. State meant to vanish goes in `doctor.ephemeralPaths` from the same module, so `doctor` does not report it as lost. State in a home goes through `home.persistence."/persist".directories` (relative to the home, `helpers.relativeToHome`), or `helpers.persistInEveryHome` from a NixOS module; it only applies on hosts with `wipe-home`.
- **State read during activation lives under `config.impermanence.persistPrefix`.** Activation scripts (sops-nix) run before the impermanence bind mounts exist: point such paths at `/persist` through the prefix, as `ssh` and `secrets` do.
- **`home-manager-<user>` fails inside `<name>-disk`.** disko's harness mounts the host store over 9p and `nix-daemon` cannot chown it; the wipe test does not wait for it, `<name>-boots` covers home-manager.
- **No key file next to `tpm2-device`.** systemd-cryptsetup then reads the key file as a TPM token and never tries the TPM. Tests unlock LUKS by typing the passphrase on the console (`modules/features/disk/unlock-disk.py`).
- **The volume key of an open LUKS2 device is not readable** through dm-crypt. `tpm2-enroll` uses the `user` copy the initrd links with `link-volume-key=`, passed as `%user:<name>`; the initrd drops it once a token exists, else after 300 s.
- **Wait for the password agent, not for its unit.** Wait for `password query on /dev/tty1`, or with Plymouth for `Please enter passphrase for disk`; keys sent earlier are lost.
- **Hyprland needs a DRM device in the VM**: `-vga none -device virtio-gpu-pci`.
- **nixos-raspberrypi's prebuilt kernels come from its own nixpkgs pin**: `features/hardware/raspberry-pi` builds the kernel and firmware from our `pkgs` (`mkOverride 900`), so its binary cache has no hit for them.
- **`nix flake check` only evaluates the current system.** Evaluate `aarch64-linux` checks with `nix eval` and let CI build them.
- **Unfree packages go through `nixpkgs.config.allowUnfreePackages`** : a module adds its `lib.getName` to the list; `allowUnfree = true` would make every list moot. The boot test runs with `node.pkgsReadOnly = false` so host `nixpkgs.*` settings apply.
- `warning: unknown flake output 'modules'` is expected and harmless.

## CI

Workflows in `.github/workflows/` only chain one-line calls. Any logic goes into Nix (`flake.ci.*`) or into a shell script under `modules/flake/ci/` (or the folder of its tool, such as `modules/flake/upstream/`), packaged with `writeShellApplication` and called with `nix run .#<name>`. Never write a multi-line script inside a workflow. The `ci-ok` job is the single required status check on `main`. `release` runs in the starter only and `sync-upstream` in forks only, both keyed on `github.repository`; `sync-upstream` also waits for the fork to set `SYNC_UPSTREAM` to `true`. Details: `docs/ci.md`.

## Conventions

- **No comments** in `.nix` and `.sh` files: names carry the intent. Tool directives stay. One exception: the example hosts (`example`, `example-server`, `example-pi` in `modules/hosts/`) and the example person (`modules/users/alice`) are commented, read top to bottom by a forker. In each example host, every registry field has one or two lines, and every profile, feature, hardware module and app the starter ships has one line, enabled or commented out; in the example person, every person field has one or two lines. **A change that adds or renames a registry field, a person field, a profile, a feature, a hardware module or an app updates all three example hosts (or the example person) in the same commit**, and `docs/options.md` with `nix run .#options-doc`; a commented line never changes what the host builds. The `example-hosts` check (`modules/flake/hosts/examples-check.nix`) fails on a missing line and names it.
- Code, docs, commits and README in English. No em dash or en dash anywhere.
- Conventional Commits (`feat`, `fix`, `refactor`, `docs`, `chore`, `ci`), subject describing the observable effect, lowercase, no trailing period, at most 72 characters; prose body explaining why when not trivial. release-please opens the release PR on `main`: never set a version, edit `.release-please-manifest.json`, `version.txt` or `CHANGELOG.md`, or create a tag by hand. The project stays in `0.x` with every release marked as a pre-release until the maintainer decides on `1.0.0`.
- Branches `feat/`, `fix/`, `refactor/`, `chore/`, `docs/` from `develop`; PR into `develop`, then `develop` into `main` with a merge commit, never squashed. `main` only moves through PRs.
- `ROADMAP.md` lists shipped lots and their guardrail checks; update it in the commit that ships a lot.
- The pre-push hook runs treefmt, `nix flake check --no-build` and actionlint in seconds; builds and boot tests are left to CI. Never bypass it with `--no-verify`.
- Stage files one by one. Never commit or push without the maintainer's explicit go: show the staged diff and wait.

## Safety

Everything is developed and tested in VMs. Never run disko, `nixos-install`, `nixos-rebuild switch`, `bootctl`, `sbctl` or any partitioning command against a physical disk or the host machine without an explicit request naming the target.

## Done means

1. `nix fmt` leaves nothing to change and `nix flake check -L` ends with `all checks passed!`
2. `nix run nixpkgs#actionlint` is clean when workflows changed
3. A change with an observable effect is shown running: VM boot, `closure-diff`, command output
4. README and `docs/` still match the code
